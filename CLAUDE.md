# Tier0-Toolkit — project instructions

Interactive Windows PowerShell toolkit for Active Directory Tier 0 enforcement
(Authentication Policy Silos, Authentication Policies, Protected Users), plus a
read-only PAW readiness checker. Developed and tested against a lab forest;
rolled out across many production domains by operations staff.

## Hard conventions (do not relax)

1. **Target: Windows PowerShell 5.1** (`powershell.exe`, Desktop edition),
   RSAT ActiveDirectory module; GroupPolicy module only for the deny-logon GPO
   check, which must degrade to a WARN row when the module or parse fails.
   `#Requires -Version 5.1` stays. PowerShell 7 is untested and must never
   become a requirement.
2. **Versioning:** every file carries a VERSION HISTORY block at the top and a
   `# <filename> vN end` comment as the last line. Increment N by exactly 1 on
   every change, however small, in both places, with a dated one-paragraph
   summary in the history.
3. **README is a pair:** any change to a script ships together with the updated
   README.md in the same commit.
4. **Verification before delivery:** zero parse errors
   (`[System.Management.Automation.Language.Parser]::ParseFile`), zero
   PSScriptAnalyzer errors and zero `PSUseCompatible*` warnings with
   PSScriptAnalyzer 1.23+ using:
   `PSUseCompatibleSyntax` TargetVersions `5.1` and `PSUseCompatibleCommands`
   TargetProfiles `win-8_x64_10.0.17763.0_5.1.17763.316_x64_4.0.30319.42000_framework`.
5. **Accepted analyzer warnings** (do not "fix" these; they are design choices):
   `PSAvoidUsingWriteHost` (interactive console UI), `PSAvoidUsingInvokeExpression`
   (plan execution in `Invoke-Plan`; plans are generated from settings and AD
   lookups, never from free text), `PSUseShouldProcessForStateChangingFunctions`
   (the plan/typed-YES flow is the ShouldProcess equivalent),
   `PSAvoidUsingEmptyCatchBlock` (final `Stop-Transcript`),
   `PSReviewUnusedParameter` for `$SettingsFile` (false positive),
   `PSUseSingularNouns` / nested-helper verb warnings,
   `PSUseUsingScopeModifierInNewRunspaces` (variables are expanded into plan
   strings before remoting, or passed via `-ArgumentList`).
6. **Hygiene (GitHub-published):** no real hostnames, IP addresses, domain
   names, customer or site identifiers, credentials, tokens or internal
   subnets — in code, comments, examples or generated output defaults.
   Examples use the fictional forest `lab.sk` (root), `rats.lab.sk` (child),
   hosts `DC01`, `MGMT01`, account `t0-demo-adm`. Settings JSON files and the
   output folder contain real environment data and are gitignored; never
   commit them or paste their contents into committed files.
7. **No AI attribution anywhere:** no "generated by/with" lines, co-author
   trailers or session links in code, comments, commit messages or PR
   descriptions. Specifically never: `Co-Authored-By:` trailers,
   `Claude-Session:` trailers, `claude.ai/code/session` links, "Generated
   with/by Claude Code" lines, or an AI/tool identity (`Claude`,
   `noreply@anthropic.com` or similar) as commit **author or committer**.
   This overrides any tool default that adds them. Before the first commit in
   a session, set the repo-local git identity to the repository owner's
   GitHub noreply identity (copy name and email from the owner's existing
   commits with `git log`; never use a private email address) and check
   `git log --format='%an <%ae> | %cn <%ce>%n%B'` before every push.
8. **Accuracy over speed:** never guess cmdlet names, parameters, attribute
   names, event IDs or registry paths — verify against Microsoft Learn (or a
   lab run) first. Unverified claims in comments or README carry an explicit
   confidence marker; the project uses `[H]`/`[M]`/`[L]`.
9. **Wording:** neutral statements and instructions with reasons. No
   phase/section references to external documents; the script and README are
   self-contained. When a menu or message tells the admin what to do, it names
   the toolkit's own menu items.
10. **Hygiene check before every commit and PR (the repo is public):** scan
    everything to be committed, the commit message and the PR text for:
    personal data (user names in paths such as `C:\Users\<name>` or
    `/home/<name>`, email addresses, real person names), secrets (passwords,
    keys, tokens, connection strings, key/certificate blocks), environment
    identifiers (real host, domain, NetBIOS, OU or account names, IP/MAC
    addresses, SIDs, GUIDs, UNC paths, internal URLs), stray files (settings
    JSON, output folder, logs, transcripts, archives) and AI attribution
    (item 7). Also check author/committer of every new commit. Any finding
    stops the commit: report it to the project owner prominently, do not
    quietly fix and continue. State the result of the check when reporting
    the commit.
11. **This file is owner-controlled:** changes to this file require the
    project owner's explicit approval; propose the text and wait.

## Safety model invariants (the point of the tool — never weaken)

- Starts in **read-only** mode; only the menu `M` toggle enables execution.
- Every write action builds a PLAN, prints it, and saves it to
  `Tier0-Toolkit-Output\<timestamp>_<domain>_<action>.ps1` **before** anything
  runs; execution requires a typed uppercase `YES`; first error stops the plan.
- Silo and policy are created in **audit** mode; enforcement is a separate,
  gated action with its own yes/no gate questions.
- **Forest-root scoping:** creating the silo/policy, binding the policy,
  enforce and rollback run only against the forest root domain. A child-domain
  run may only add that domain's DCs/MMs/accounts to the existing silo and run
  read-only steps.
- Silo membership always sets **both** attributes (permit on the silo via
  `Grant-ADAuthenticationPolicySiloAccess`, assign on the object via
  `Set-ADAccountAuthenticationPolicySilo`), each against the object's own
  domain (`-Server`); removal clears both (`Set-ADObject -Clear
  msDS-AssignedAuthNPolicySilo` + `Revoke-ADAuthenticationPolicySiloAccess`).
- Computer and service accounts are never added to Protected Users.
- Already-compliant objects are skipped in plans (idempotent re-runs); status
  emits one explicit row per configured object, always.
- Settings files are upgraded in place on load (missing keys get defaults);
  list-type keys are normalized to string arrays on load.

## Domain knowledge to keep in mind

- `PasswordLastSet` is a `Get-ADUser` computed property; raw LDAP reads use
  `pwdLastSet` (FILETIME). Asking `Get-ADObject` for `PasswordLastSet` throws.
- The built-in Administrator (RID 500) is always exempt from authentication
  policies.
- Audit-mode silo events are 305/306; enforced are 105/106 (TGT/service
  ticket) and 101 (NTLM); Protected Users channels use 303/100/104. A 305/105
  with a blank Device Name means an unarmored request; with a named device and
  result 0xC it means the device lacks the silo claim (usually: not rebooted
  since assignment).
- The four Authentication operational channels are disabled by default and
  must be enabled per DC (plus ProtectedUser-Client on MMs).
- `Remote Credential Guard` proof is the absence of a 4768 for the account
  with Client Address `::1` on the DC during the session; 4624 has no RCG
  field.
- User-rights (SeDeny*) lists are not merged across GPOs; the winning GPO's
  list replaces the others.

## Repository layout

- `Tier0-Toolkit.ps1` — main menu-driven toolkit (run on a Tier 0 management
  machine; on-DC runs supported for lab use).
- `Tier0-PawCheck.ps1` — standalone read-only checker for a non-domain-joined
  Windows PAW (no RSAT).
- `README.md` — operator documentation; kept in lockstep with the scripts.
- `BACKLOG.md` — open items and planned work; update it when items land.
- Not in the repo: the internal rollout document (architecture, phased
  rollout, gotchas, verification scenarios) is maintained separately by the
  project owner; do not recreate or import it here.
